The shape

Not eight projects. One engine that grows a layer at a time.

Scattered projects read as scattered. A single engine that gains a capability every three weeks reads as engineering — and it lets each stage be judged on its own terms, because each one ends with a number or a proof rather than a commit log.

The spine below is the engine. Stage 05 is a companion binary that shares its allocator and tensor code but runs backward instead of forward. The two satellites aren't scheduled work — they're things that become possible once stage 02 exists, and both are nearly free by then.

The spine

Five stages, in dependency order.

Every figure in the gates panels is a target to be measured, not a measurement. A stage isn't done when the code runs — it's done when the gate is met and the number is written down, including when the number disappoints.

01

A correct forward pass, in 2,000 lines of C99

2 weeks
UnderstandingFoundation for everything

Pure C99, zero dependencies, one binary. A modern Llama-family architecture — not the 2023 one — so you meet grouped-query attention, RoPE, RMSNorm, SwiGLU and per-head QK normalization the way current models actually use them.

  • Real GGUF parsing over mmap, zero-copy. Not a toy .bin dump — this is what lets you load anything off Hugging Face for the rest of the project.
  • An arena allocator and a tensor descriptor struct. Every later stage inherits these, so get the memory model right once.
  • A real BPE tokenizer with merge ranks and byte fallback. Most from-scratch attempts skip this and hardcode a vocab; it's the part that makes your engine usable on arbitrary text.
  • KV cache, then sampling: greedy, temperature, top-p, min-p.

02

Quantization and hand-written SIMD, on two ISAs

3 weeks
PortfolioResearchThe highest-leverage stage

This is the stage that gets you hired, and the one your second machine makes uniquely yours: the same kernel, written twice, benchmarked honestly against each other. Very few people can produce that table.

Implement the block formats for real — Q8_0 (32 weights + one fp16 scale = 34 B), Q4_0 (32 weights + scale = 18 B), then the K-quant superblock: Q4_K packs 256 weights as eight sub-blocks with 6-bit scales and mins plus an fp16 super-scale, landing at 4.5 bits/weight.

  • Write the quantizer too, fp32 GGUF → Q4_K GGUF, including an importance-matrix calibration pass so the quality claim is defensible.
  • Treat prefill and decode as two different problems, because they are: decode is a memory-bound GEMV, prefill is a compute-bound tiled GEMM. Conflating them is the most common mistake.
  • Dequantize inside the inner loop. Never materialize fp16 weights to memory — the compression ratio is the speedup on a bandwidth-bound decode.
  • NEON on the M1: vdotq_s32, nibble unpack via vandq_u8/vshrq_n_u8. AVX2 on x86: _mm256_maddubs_epi16 with a _mm256_shuffle_epi8 nibble LUT; AVX-512 VNNI: _mm512_dpbusd_epi32.
  • pthreads with a real barrier. Measure scaling across the M1's 4 performance + 4 efficiency cores — they are not interchangeable, and your speedup curve will show it.

03

A Metal backend for the M1 GPU

3 weeks
PortfolioPlatform depth

On Apple silicon the GPU, not the AMX coprocessor, is where inference belongs — published measurements put the M1 Max GPU around 4.7× the AMX blocks on the same workload. Driving Metal from C is a genuinely uncommon skill.

  • A thin Objective-C bridge (or metal-cpp) exposing a C API: buffer, pipeline, dispatch. Keep the C side ignorant of Metal types.
  • Kernels: fused dequant + matvec, an online-softmax fused attention, RMSNorm, RoPE, SwiGLU. Same rule as stage 02 — dequantize in-register, never to global memory.
  • Introduce a backend vtable so CPU and Metal are swappable at runtime. You'll rediscover from the inside why ggml is structured the way it is.
  • Unified memory is the M1's cheat code: no host↔device copy. Exploit it, and say so in the write-up.

04

The serving layer that makes it a product

3 weeks
Ship itSystems design

Stages 01–03 make a fast program. This one makes a server, and it's where the OS-flavoured ideas live — the same virtual-memory trick vLLM made famous, implemented by you, in C, where it's most natural.

  • Paged KV cache: fixed-size physical blocks plus a per-sequence block table, so fragmentation stops capping concurrency.
  • Continuous batching: schedule at iteration granularity, not request granularity. Finished sequences leave the batch mid-flight and new ones join.
  • Prefix cache: a radix tree over token prefixes so a shared system prompt is prefilled once for every request that follows.
  • An OpenAI-compatible /v1/chat/completions with SSE streaming, so every existing client works against your engine with a changed base URL. That single decision is what turns a demo into something people run.

05

Backward passes, derived by hand

3 weeks
UnderstandingCompanion binary

The deepest stage, and the one PyTorch has been hiding from you. There is no autodiff — you derive and write every backward yourself, then prove each one numerically. Nobody who finishes this is ever again vague about what a transformer does.

  • Backward for matmul, RMSNorm, RoPE, softmax-attention, SwiGLU, cross-entropy. Derive on paper first; the code is the easy half.
  • AdamW with decoupled weight decay, cosine schedule with warmup, global-norm gradient clipping.
  • Train on TinyStories to a real loss curve and coherent samples. A small model that genuinely learns beats a large one that half-runs.
  • Shares stage 01's arena and tensor code — that reuse is itself the argument that the foundation was built right.

The 8 GB constraint

Memory picks your models, and bandwidth picks your ceiling.

Q4_K lands near 0.6 bytes per parameter once the K-quant mix and metadata are counted. Add the KV cache and the OS, and 8 GB of unified memory draws a hard line through the model list.

Why decode speed is arithmetic, not luck

Autoregressive decode reads every weight once per token, so it is bandwidth-bound. That gives you a ceiling before you write a line of kernel — and a way to know when to stop optimizing.

M1 memory bandwidth ≈ 68 GB/s Qwen3-0.6B @ Q4_K 0.4 GB → ceiling ≈ 170 tok/s SmolLM3-3B @ Q4_K 1.9 GB → ceiling ≈ 36 tok/s Llama-3.1-8B @ Q4_K 4.9 GB → ceiling ≈ 14 tok/s

Hit 60–70% of the ceiling and the remaining work is in prefill, not decode. This single calculation is also the honest answer to "why is quantization worth it" — at Q4 you move a quarter of the bytes, so you get roughly four times the tokens.

Deliberately excluded

Two projects that would otherwise be here

CUDA kernel work / llm.c-style multi-GPU training. Cut because you have no NVIDIA GPU and didn't ask to rent one. If that changes, it slots in after stage 02 — the quantization and tiling intuitions transfer directly, and only the memory hierarchy is new.

Transformers on a microcontroller. Cut because you don't have a board. It's the most memorable portfolio piece in the whole space and the cheapest to unblock — an ESP32-S3 is roughly the price of lunch. Say the word and it becomes a sixth stage: static arenas, no malloc, int8 end to end.
